# Spott.ca

Canadian local-commerce super-app: business directory (Yelp-style) + marketplace
classifieds (Kijiji/FB Marketplace-style) + a vehicle hub (AutoTrader-style),
plus two AI assistants: **Sparq** (public, user-facing) and **Zeus** (admin-only).

Built with Lovable (lovable.dev) and continues to be edited by hand / by Claude Code.
There is a `Spott_Full_Build_Report.html` floating around (Downloads folder) that
reads like a product one-pager — it describes several features (a full "Zeus God
Mode" chat, a Sparq business-embed widget, voice/live mode, a `haiku_audit_log`
audit trail) that **do not exist in the code**. Treat that file as aspirational
marketing copy, not a spec. Verify claims against `src/` before trusting them.

## Stack
- TanStack Start v1 + React 19, file-based routes in `src/routes/*.tsx` (dot-separated
  filenames, e.g. `admin.sparq.tsx` → `/admin/sparq`). `src/routeTree.gen.ts` is
  auto-generated by the router's Vite plugin on `vite dev`/`vite build` — don't hand-edit it,
  and don't be alarmed if it's dirty in `git status`.
- Vite 7 + Tailwind v4. Supabase (Lovable Cloud) for DB/Auth/Storage — RLS everywhere,
  roles live in `user_roles` (never on `profiles`), checked via `has_role()`.
- Stripe embedded checkout for billing. Lovable AI Gateway (Gemini) for Sparq/Zeus.
- `npx vite build` / `npx tsc -p tsconfig.json` both work from a plain npm install;
  a `bun.lock` and `bunfig.toml` also exist in the repo — check which is currently
  in active use before assuming one over the other.

## Admin panel conventions
- Every admin page wraps in `<AdminShell>` (`src/components/admin/AdminShell.tsx`),
  which also owns the **sidebar `NAV` array** — add new admin routes there or they're
  unreachable from the UI even if the route file exists.
- Many admin routes are literally `<AdminPlaceholder>` stubs pointing at `/admin/legacy`
  ("legacy admin" tabs) for real data — check whether a page is a placeholder before
  assuming a feature is live.
- Server-side data access goes through `createServerFn` in `src/lib/*.functions.ts`,
  called from route components via `useServerFn(fn)`. Admin-gated functions check
  `has_role('admin')` inside the handler, not just in the UI.

## Sparq & Zeus (the AI layer)
- Isolated under `src/routes/api/sparq*.ts` / `zeus*.ts` and `src/lib/sparq-*` so it
  can be split out later without touching marketplace/directory code.
- `sparq.chat.ts` — public text chat, trial-gated (`TEXT_FREE_LIMIT` msgs/month via
  `haiku_usage`). System prompt is assembled by `buildSystemPrompt()`, which layers:
  built-in prompt (or `system_prompt_override` if an admin set one) → strict-mode
  clause → off-topic redirect line → admin additional rules → additional instructions.
  Every turn is logged to `haiku_conversations`/`haiku_messages` via `logTurn()` for
  the `/admin/sparq-learning` transcript viewer — logging is best-effort and must
  never throw into the user-facing response.
- `sparq.image.ts` — Pro-gated image gen; prompt gets a brand style prefix appended
  server-side since the image model has no system-role support.
- `sparq.social.ts` / `zeus.social.ts` — near-duplicate social-post generators (owner
  vs admin-facing). Keep their brand-voice rules in sync if you edit one.
- `/admin/sparq` and `/admin/sparq-learning` (both added by Claude Code, not Lovable)
  are the control surface for the above — before this, `sparq-settings.functions.ts`
  and `sparq-learning.functions.ts` were fully implemented but called by nothing.
- Zeus today is genuinely just `/zeus` (a stub landing page) + `/zeus/social`
  (the admin equivalent of Sparq's social generator). It is **not** the "full god-mode
  assistant" the build report describes — building that out would be a real, separate
  feature project, not a prompt tweak.
